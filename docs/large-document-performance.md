# 大文档卡顿治理方案

## 现象与初步结论

测试文件 `F:\Desktop\ceshi3\releases.md` 约 923 KiB、1.66 万行，包含约 5,400 个列表项；`THIRD-PARTY-NOTICES.md` 约 2.3 MiB、5.46 万行，列表项约 3,200 个。文件字节数和行数不能直接代表编辑器成本。大量短列表项会构成许多独立块，并增加解析、元数据遍历和派生数据生成开销。

当前编辑器已经实现按滚动位置裁剪块元素，但这不等于整篇文档按需加载：打开时仍同步解析并建立完整块树；每帧仍扫描全部块构造行计划/估算高度；内容修改后指纹、Markdown 序列化、源码映射及引用定义可能全篇重算。因此“当前页加上下页”是正确的渲染优化方向，但本身不能解决打开和输入时的全篇工作。

## 目标

- 打开大文档时尽快出现可交互窗口，避免主线程长时间不出帧导致透明窗口。
- 滚动绘制成本主要随视口附近块数增长，而不是随文档总块数逐帧增长。
- 编辑一个块时避免同步重建与该块无关的整篇派生数据。
- 保持 Markdown 结构、保存结果、查找/替换、源码视图、撤销重做、焦点导航和滚动位置正确。
- 用不同结构的长文档验证，而非只按文件大小设阈值。

## 分阶段方案

### 1. 建立可复现基线

记录文件字节数、行数、根/可见块数、打开首帧时间、可输入时间、单字符编辑延迟、滚动帧耗时和内存峰值。至少覆盖大量列表项、长段落、代码围栏、表格/嵌套块等不同语料。计时应区分读取、解析建树、首帧布局和首次派生数据计算。

### 2. 降低每帧全篇扫描

复用行分组计划、行首索引和高度前缀数据；仅在文档结构、分组语义或列宽变化时重建。视口定位用前缀高度二分查找，只挂载当前视口及上下缓冲区，并保留焦点块。高度未知时采用估值并在测量后修正滚动锚点，避免跳动。高度索引应支持块高度变化和结构插入/删除。

### 3. 降低编辑后的全篇重算

让单块内容版本变化只使该块相关的序列化范围、映射和统计失效；跨块引用定义等确实依赖全篇的结果采用延迟/后台刷新或可验证的增量索引。状态栏统计、查找索引和保存数据应按需计算，不能阻塞每次按键。

### 4. 缩短打开阻塞

优先把纯文本读取、分词/语法识别和轻量中间表示移至后台；主线程分批将视口附近块建成 UI 实体，先展示顶部并可交互，再按预算构建后续区域。若完整解析不可避免，至少分帧构建，显示明确加载态。保存与编辑必须始终覆盖未挂载区域，不能把“未渲染”误作“未加载/未保存”。

## 实施顺序与边界

先检查并优化现有虚拟化的每帧全量行计划与高度查询，再处理编辑时全篇派生数据，最后评估增量解析/分帧建树。后两项涉及文档模型、来源映射及撤销语义，不能以仅隐藏屏外元素替代。

不采用固定“页码”作为核心单位：编辑器没有稳定分页，字体/窗口宽度/内容高度变化都会改变页边界。以像素视口加上下缓冲区和稳定滚动锚点为准。

## 验收

- `releases.md` 与 `THIRD-PARTY-NOTICES.md` 均可正常打开、编辑、滚动、保存和重新打开。
- 长文档空闲帧不逐块重建行计划；视口外块不创建渲染元素。
- 连续输入时无明显停顿，结构编辑后光标与滚动锚点稳定。
- 源码/渲染视图切换、搜索替换、撤销重做、全选复制和引用链接行为保持一致。
- 记录优化前后各阶段耗时及块数，避免只凭主观感受判断。

## 当前进展

第一阶段已实现：渲染行计划（行分组、行首索引、间距与首块 ID）按文档树修订号缓存；滚动与普通重绘帧复用缓存，并以修订号 O(1) 判断结构变化，只有结构变化时才刷新可见块 ID 快照。

针对用户观察到的 3～4 秒透明窗口，增加 128 KiB 阈值：大型文档先打开带“正在加载大型文档…”提示的轻量窗口，等待 100ms 让首帧呈现，再在 UI 线程构建完整块树。加载期间暂不关联文件路径，避免占位文案被快捷保存覆盖到源文件；完成后由正常重建流程恢复路径和编辑状态。

后续改为增量批处理：每次 UI 更新最多解析 32 个根块，列表仅在完整列表项之间暂停；实体先放入待载入缓冲区，不对半成品开放编辑或保存。批次间隔 2ms 让出事件循环，完成后一次性替换根树。超大单个块（如一整段或一个超长代码围栏）仍作为单块解析，最终全树元数据/运行时重建也仍是一次性工作。

分批载入完成时保留规范化输入作为稳定历史快照，不为初始化历史而立即重新序列化并构建源码映射；常规小文档构造与同步替换仍保留原有快照刷新语义。大型文档的选区映射由第一次需要它的渲染/编辑路径生成。

首帧渲染原本会为捕获光标源码位置立即构造整篇派生映射，状态栏又会访问同一缓存。大型分批载入现在首屏直接从保留的 Markdown 文本快速统计字数（与编辑器规范化文本可能相差少量），初始光标暂显 `1:1`；源码映射不再由空闲渲染定时触发，而是在需要精确源码位置的操作时按需刷新。空闲重绘和滚动不会触发这项全篇工作；首次相关操作仍可能承担一次性开销。

表格运行时建立引用上下文时也曾调用完整 `derived_document`。大型载入现在直接从已读取的 Markdown 文本解析图片与链接引用定义，再同步块运行时上下文；其他普通结构编辑仍走原派生缓存流程。

大于 256 个可见块时，连续文本输入走轻量撤销路径：用编辑块的内容版本确认实际变化，复用合并窗口里的旧历史文本，不在每个字符后生成整篇序列化结果；状态栏统计和稳定源码/选区映射暂缓 300ms，输入停顿后一次刷新。长时间连续输入超过撤销合并窗口时，会在下一次字符到达前先固化上一段文本，保持撤销边界。

行足迹改为 Fenwick 前缀索引：结构/宽度改变时线性重建，普通滚动帧仅更新刚测量的挂载行，并对数查询可见区间、占位高度及焦点行高度；不再逐帧创建全行高度向量或线性扫描总高度。

载入完成后的状态重置原先连续调用 `rebuild_table_runtimes` 与 `rebuild_image_runtimes`，但表格运行时重建内部已经调用后者；紧接着又显式同步一次表格轴视觉状态，而表格重建也已同步。现在移除这两次重复全树扫描/实体通知，保留一次必要的表格与图片上下文重建。

### 可复现性能基线（release 构建，两份真实文件）

新增 `src/editor/perf.rs`（`#[ignore]` 测试，显式运行）：
`RUMARK_BENCH_FILES="…releases.md;…THIRD-PARTY-NOTICES.md" cargo test -p rumark --release editor::perf -- --ignored --nocapture`。
未提供环境变量时退回两份已知样张路径，文件缺失即跳过，普通测试不受影响。

实测（本机 release、单线程，代码块高亮已改为后台计算，分批构建与完整构建已对齐）：

| 指标 | releases.md | THIRD-PARTY-NOTICES.md |
| --- | --- | --- |
| 字节 / 行 | 944,567 / 16,569 | 2,362,769 / 54,560 |
| 根块 / 可见块 | 9,850 / 10,828 | 8,955 / 8,955 |
| 读取 | 0.6ms | 1.2ms |
| 分批解析建树 | 242.5ms | 394.7ms |
| 安装（优化后） | 161.8ms | 33.1ms |
| 首次精确派生 | 85.7ms | 57.2ms |
| 保存序列化 | 0.0ms | 0.1ms |
| 首帧 | 8.7ms | 7.8ms |
| 滚动帧均 / 峰 | 10.3 / 14.1ms | 9.5 / 14.9ms |

关键发现与两轮修复：

1. **逐块通知风暴**：细分测量显示，对 10,877 个刚创建、尚未挂载的块调用 `cx.notify()` 单独耗时约 175～219ms，而同样的逐块 `update` 不通知仅约 1ms。这些块不可能有观察者，逐块通知只是纯重绘调度开销。修复：`sync_runtime_contexts_inner(false, …)` 安静写入运行时上下文（状态由 `block.update` 同步落盘），载入完成处仍统一 `notify` 一次。安装阶段 433ms → 294ms（releases.md）、297ms → 42ms（THIRD-PARTY-NOTICES.md）。

2. **无引用块的行内重解析**：定义从空变成全文集合时，`sync_link_reference_definitions` 会把每块标题序列化再全量重解析，但只有含引用式链接的块可能变化。新增 `InlineTextTree::has_link_reference_candidate()`（片段含 `[` 或已解析的 `InlineLink::Reference`），不含候选的块只保存定义、跳过重解析；同时按 `starts_with_image_marker()` 跳过独立图片运行时的两份字符串分配。安装阶段进一步 294ms → 201ms（releases.md）、42ms → 38ms（THIRD-PARTY-NOTICES.md）。releases.md 剩余成本主要是 1,375 处真实的引用式链接重解析，属正确性必需，不能省。

两轮合计安装阶段 433ms → 201ms（releases.md）。回归测试覆盖两个方向：定义新增后引用链接可解析、定义移除后快捷引用还原为字面文本（可见文本无 `[` 时靠 `Reference` 标记命中候选判断）。

### 卡顿来源归因（第三轮）

为了回答“是我们自己的代码还是第三方 crate”，基准新增了只在测试构建生效的归因探针，拆出 inline 解析、tree-sitter 高亮、块构造、根块判定、段落边界判定、段落收集及 UI 更新耗时。结论是**两份样张的主因不同**：

| 归因项 | releases.md | THIRD-PARTY-NOTICES.md |
| --- | --- | --- |
| 自身 inline 解析 | 42.7ms | 2.4ms |
| tree-sitter 高亮（第三方，但由我们同步调用） | 优化前 253.1ms → 0ms | 0.2ms → 0ms |
| 块构造（含实体创建） | 57.7ms | 21.8ms |
| `cx.update` / 实体登记 | 283.8ms | 437.2ms |

**releases.md**：最大单项是 tree-sitter 代码高亮。它不是解析 bug，而是我们在建块时对每个代码块立即同步高亮。现在代码块记录新增延迟标记，建树阶段不跑 tree-sitter；代码块首次进入渲染布局时调用 `ensure_code_highlight()`，派发到后台线程池计算，完成后回填结果并统一通知一次重绘，未回填期间按无高亮渲染。中间尝试过在渲染帧内同步计算：parse 确实降到 284.2ms，但滚动进入新代码块时又同步触发 tree-sitter，releases.md 滚动峰值从约 15.9ms 冲到 802.1ms；改为后台派发后滚动帧不再执行 tree-sitter，滚动峰值回到 13～20ms。建块阶段的 tree-sitter 耗时从 253.1ms 降到 0，parse 从 555.8ms 降到 255～326ms。无需 fork tree-sitter。

**THIRD-PARTY-NOTICES.md**：`pulldown-cmark` 只用于导出，不参与打开；`ratex` 只用于公式渲染；`cssparser` 只用于 HTML 颜色解析。该文件几乎没有行内语法和代码围栏，inline 与 tree-sitter 合计不到 3ms。剩余 437ms 几乎全部是 `cx.update` 在约 9,000 个块实体创建后的更新与登记成本，属于 rgpui 框架机制，但根因是我们为大量空行/短段落创建了过多块实体。把批次从 32 根块放大到 256 并不能降低这项总成本，反而增加单批工作，因此已回退到 32。

同时新增 inline 纯文本快路：不含 ``\ * _ ~ ^ ` < [ $ &`` 等触发符，也不含 `:shortcode:` 形态文本时，直接构造纯文本树并保留软换行折叠。9,802 次 inline 解析中 2,529 次走快路（releases.md），8,085 次中 8,051 次走快路（THIRD-PARTY-NOTICES.md）。另有段落边界判定短路：段落未出现反引号时不再为了检测未闭合代码而反复 join 整段文本。

结论：没有发现需要 fork 的第三方 Markdown 解析库。第三方 tree-sitter 的成本来自我们的调用时机，已改为按需；剩余大头来自我们自己的块实体数量和 rgpui 实体更新机制，下一步应减少不必要的实体或引入真正的分块文档模型，而不是 fork 库。

滚动与首帧已在 10～20ms 量级，非卡顿主因；渲染不随总块数线性增长的目标已达成。

### 第四轮：关闭链路实测与真实载入被定时器粒度放大（附两处正确性修复）

用户反馈"点击关闭按钮也容易卡"。这次不再只用测试环境推理，而是用 PowerShell 走真实原生路径测量：`CloseMainWindow()` 发送 WM_CLOSE，与点击标题栏 X 走完全相同的平台路径；配合轮询窗口标题、文件 mtime 与桌面截图计时。结论：

| 场景（真实应用，releases.md / THIRD-PARTY-NOTICES.md） | 实测 |
| --- | --- |
| 干净文档点击 X → 窗口消失 → 进程退出 | 9～10ms / 36ms |
| 载入中途点击 X | 8～17ms |
| 脏文档点击 X → 确认框可见 | 50～85ms |
| 确认框"保存并关闭" → 文件落盘 → 窗口消失 | 约 82ms / 约 101ms |
| 确认框"放弃并关闭" → 窗口消失 | 约 115ms |

关闭链路本身各环节都不是主因；真正的问题藏在**真实载入时长**：测试环境里 0.5s 的分批载入，真实应用要 4.4～4.8s。根因是 `defer_large_document_load` 的批间隔用了 `timer(2ms)`，而 Windows 线程池定时器默认约 15.6ms 才传递一次过期（rgpui 的 `increase_timer_resolution` 只覆盖 park 路径，不覆盖 `dispatch_after`），282～308 个批次每个都付出一个完整粒度。修复：每个 tick 按时间预算（8ms）连续处理多个批次再让出主线程，tick 数成倍减少，实测载入 4.75s → 0.99s、4.8s → 1.18s，UI 响应不受影响。

修复过程中补上的对拍基线（分批构建 vs 一次完整构建，含真实样张 `chunked_build_matches_full_parse_on_samples`）暴露了两处此前未发现的正确性问题：

1. **批次边界块树漂移**：空行保留规则用 `roots.is_empty()` 判断"文档开头"，但每个新批次的 roots 都从空开始，导致每批边界多出空段落（releases.md 49 个、THIRD-PARTY-NOTICES.md 90 个）；列表组分隔空行数量也因跨批丢失"上一根块是列表项"上下文而漂移。修复：空行规则改为 `start == 0` 才适用文档开头语义，并跨批携带列表项上下文。
2. **列表项续行文本被逐行解析**：首行残缺解析（未闭合反引号定型为字面量）+ 续行按树合并，跨行代码段永远无法成立；载入完成后的引用重解析再把残缺序列化文本当作合法引用链接整体解析，反引号被转义、尖括号内容被行内 HTML 解析吞掉——releases.md 实测 `[RFC 1358]` 变成 `[RFC 1358][RFC 1358]`、代码段内容损坏，**保存时写进文件**。修复：续行文本进入缓冲，在条目结束/提升判定处一次性解析；引用式链接的序列化同时改为忠实还原快捷 `[标签]`、折叠 `[标签][]`、完整 `[标签][引用]` 三种源码形式（此前快捷/折叠一律展开成完整形式，是旧测试固化下来的行为，本轮按数据完整性优先原则修正）。

对拍与回归覆盖：`deferred_large_document_load_completes_in_budgeted_chunks`（标题密集 + 列表密集合成样张，断言分批与完整构建的块数与序列化一致）、`chunked_build_matches_full_parse_on_samples`（真实样张对拍）、`reference_link_forms_round_trip_faithfully`（三种引用形式往返一致）。

### 第五轮：交互路径基线与视图切换的 O(块×定义) 同步

新增 `large_document_interaction_profile`（编辑帧 / 停顿刷新 / 视图切换 / 查找）与 `large_document_view_toggle_breakdown`（切换细分）。单字符编辑帧 3～6ms、查找扫描 5～13ms、输入停顿后的稳定快照刷新 60～99ms，均非卡顿主因。**源码视图切回渲染视图实测 1.0～3.6 秒冻结**，细分归因：

| 切回渲染（releases.md） | 修复前 | 修复后 |
| --- | --- | --- |
| 全量重建 9,850 块（单次 update） | 643ms | 409ms |
| 表格 + 引用同步（含 derived 重建） | 453ms | 走安静路径 |
| 引用同步（第二次，独立调用） | **3,116ms** | 12.3ms（合并入上一步） |

根因不在行内重解析（细分探针显示 3.1 秒的引用同步 inline 解析为 0 次），而在 `sync_link_reference_definitions` / `sync_footnote_registry` 的**逐块深度相等比较**：releases.md 有 1,505 条引用定义，每次全量同步对每块比较整个定义表，O(块数 × 定义数) ≈ 1,600 万次比较 ≈ 3.5 秒；且内容相等时早退却不采纳新 Arc，指针永不收敛，每次全量同步都重复付出。修复：

1. **编辑器侧保证"内容未变 → Arc 指针不变"**：派生重算时定义集合与上次内容一致则复用旧 Arc（derive.rs）；`rebuild_image_runtimes_from_source` / `rebuild_footnote_registry` 同样只在内容真变时替换。
2. **块侧同步先走 `Arc::ptr_eq` 短路**，深度相等时收下新 Arc 让指针收敛（editing/mod.rs）。
3. 切回渲染改走载入同款的安静同步（`rebuild_table_runtimes_from_source`），去掉万级逐块通知与重复的第二次引用同步。
