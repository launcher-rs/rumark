# 大文档卡顿治理方案

## 现象与初步结论

测试文件 `F:\Desktop\ceshi3\releases.md` 约 923 KiB、1.66 万行，包含约 5,400 个列表项；`THIRD-PARTY-NOTICES.md` 约 2.3 MiB、5.46 万行，列表项约 3,200 个。文件字节数和行数不能直接代表编辑器成本。大量短列表项会构成许多独立块，并增加解析、元数据遍历和派生数据生成开销。

当前编辑器已经实现按滚动位置裁剪块元素，但这不等于整篇文档按需加载：打开时仍同步解析并建立完整块树；每帧仍扫描全部块构造行计划/估算高度；内容修改后指纹、Markdown 序列化、源码映射及引用定义可能全篇重算。因此“当前页加上下页”是正确的渲染优化方向，但本身不能解决打开和输入时的全篇工作。

## 目标

- 打开大文档时尽快出现可交互窗口，避免主线程长时间不出帧导致透明窗口。
- 滚动绘制成本主要随视口附近块数增长，而不是随文档总块数逐帧增长。
- 编辑一个块时避免同步重建与该块无关的整篇派生数据。
- 保持 Markdown 结构、保存结果、查找/替换、源码视图、撤销重做、焦点导航和滚动位置正确。
- 用不同结构的长文档验证，而非只按文件大小设阈值。

## 分阶段方案

### 1. 建立可复现基线

记录文件字节数、行数、根/可见块数、打开首帧时间、可输入时间、单字符编辑延迟、滚动帧耗时和内存峰值。至少覆盖大量列表项、长段落、代码围栏、表格/嵌套块等不同语料。计时应区分读取、解析建树、首帧布局和首次派生数据计算。

### 2. 降低每帧全篇扫描

复用行分组计划、行首索引和高度前缀数据；仅在文档结构、分组语义或列宽变化时重建。视口定位用前缀高度二分查找，只挂载当前视口及上下缓冲区，并保留焦点块。高度未知时采用估值并在测量后修正滚动锚点，避免跳动。高度索引应支持块高度变化和结构插入/删除。

### 3. 降低编辑后的全篇重算

让单块内容版本变化只使该块相关的序列化范围、映射和统计失效；跨块引用定义等确实依赖全篇的结果采用延迟/后台刷新或可验证的增量索引。状态栏统计、查找索引和保存数据应按需计算，不能阻塞每次按键。

### 4. 缩短打开阻塞

优先把纯文本读取、分词/语法识别和轻量中间表示移至后台；主线程分批将视口附近块建成 UI 实体，先展示顶部并可交互，再按预算构建后续区域。若完整解析不可避免，至少分帧构建，显示明确加载态。保存与编辑必须始终覆盖未挂载区域，不能把“未渲染”误作“未加载/未保存”。

## 实施顺序与边界

先检查并优化现有虚拟化的每帧全量行计划与高度查询，再处理编辑时全篇派生数据，最后评估增量解析/分帧建树。后两项涉及文档模型、来源映射及撤销语义，不能以仅隐藏屏外元素替代。

不采用固定“页码”作为核心单位：编辑器没有稳定分页，字体/窗口宽度/内容高度变化都会改变页边界。以像素视口加上下缓冲区和稳定滚动锚点为准。

## 验收

- `releases.md` 与 `THIRD-PARTY-NOTICES.md` 均可正常打开、编辑、滚动、保存和重新打开。
- 长文档空闲帧不逐块重建行计划；视口外块不创建渲染元素。
- 连续输入时无明显停顿，结构编辑后光标与滚动锚点稳定。
- 源码/渲染视图切换、搜索替换、撤销重做、全选复制和引用链接行为保持一致。
- 记录优化前后各阶段耗时及块数，避免只凭主观感受判断。

## 当前进展

第一阶段已实现：渲染行计划（行分组、行首索引、间距与首块 ID）按文档树修订号缓存；滚动与普通重绘帧复用缓存，并以修订号 O(1) 判断结构变化，只有结构变化时才刷新可见块 ID 快照。

针对用户观察到的 3～4 秒透明窗口，增加 128 KiB 阈值：大型文档先打开带“正在加载大型文档…”提示的轻量窗口，等待 100ms 让首帧呈现，再在 UI 线程构建完整块树。加载期间暂不关联文件路径，避免占位文案被快捷保存覆盖到源文件；完成后由正常重建流程恢复路径和编辑状态。

后续改为增量批处理：每次 UI 更新最多解析 32 个根块，列表仅在完整列表项之间暂停；实体先放入待载入缓冲区，不对半成品开放编辑或保存。批次间隔 2ms 让出事件循环，完成后一次性替换根树。超大单个块（如一整段或一个超长代码围栏）仍作为单块解析，最终全树元数据/运行时重建也仍是一次性工作。

分批载入完成时保留规范化输入作为稳定历史快照，不为初始化历史而立即重新序列化并构建源码映射；常规小文档构造与同步替换仍保留原有快照刷新语义。大型文档的选区映射由第一次需要它的渲染/编辑路径生成。

首帧渲染原本会为捕获光标源码位置立即构造整篇派生映射，状态栏又会访问同一缓存。大型分批载入现在首屏直接从保留的 Markdown 文本快速统计字数（与编辑器规范化文本可能相差少量），初始光标暂显 `1:1`；源码映射不再由空闲渲染定时触发，而是在需要精确源码位置的操作时按需刷新。空闲重绘和滚动不会触发这项全篇工作；首次相关操作仍可能承担一次性开销。

表格运行时建立引用上下文时也曾调用完整 `derived_document`。大型载入现在直接从已读取的 Markdown 文本解析图片与链接引用定义，再同步块运行时上下文；其他普通结构编辑仍走原派生缓存流程。

大于 256 个可见块时，连续文本输入走轻量撤销路径：用编辑块的内容版本确认实际变化，复用合并窗口里的旧历史文本，不在每个字符后生成整篇序列化结果；状态栏统计和稳定源码/选区映射暂缓 300ms，输入停顿后一次刷新。长时间连续输入超过撤销合并窗口时，会在下一次字符到达前先固化上一段文本，保持撤销边界。

行足迹改为 Fenwick 前缀索引：结构/宽度改变时线性重建，普通滚动帧仅更新刚测量的挂载行，并对数查询可见区间、占位高度及焦点行高度；不再逐帧创建全行高度向量或线性扫描总高度。

载入完成后的状态重置原先连续调用 `rebuild_table_runtimes` 与 `rebuild_image_runtimes`，但表格运行时重建内部已经调用后者；紧接着又显式同步一次表格轴视觉状态，而表格重建也已同步。现在移除这两次重复全树扫描/实体通知，保留一次必要的表格与图片上下文重建。

### 可复现性能基线（release 构建，两份真实文件）

新增 `src/editor/perf.rs`（`#[ignore]` 测试，显式运行）：
`RUMARK_BENCH_FILES="…releases.md;…THIRD-PARTY-NOTICES.md" cargo test -p rumark --release editor::perf -- --ignored --nocapture`。
未提供环境变量时退回两份已知样张路径，文件缺失即跳过，普通测试不受影响。

关键发现与两轮修复：

1. **逐块通知风暴**：细分测量显示，对 10,877 个刚创建、尚未挂载的块调用 `cx.notify()` 单独耗时约 175～219ms，而同样的逐块 `update` 不通知仅约 1ms。这些块不可能有观察者，逐块通知只是纯重绘调度开销。修复：`sync_runtime_contexts_inner(false, …)` 安静写入运行时上下文（状态由 `block.update` 同步落盘），载入完成处仍统一 `notify` 一次。安装阶段 433ms → 294ms（releases.md）、297ms → 42ms（THIRD-PARTY-NOTICES.md）。

2. **无引用块的行内重解析**：定义从空变成全文集合时，`sync_link_reference_definitions` 会把每块标题序列化再全量重解析，但只有含引用式链接的块可能变化。新增 `InlineTextTree::has_link_reference_candidate()`（片段含 `[` 或已解析的 `InlineLink::Reference`），不含候选的块只保存定义、跳过重解析；同时按 `starts_with_image_marker()` 跳过独立图片运行时的两份字符串分配。安装阶段进一步 294ms → 201ms（releases.md）、42ms → 38ms（THIRD-PARTY-NOTICES.md）。releases.md 剩余成本主要是 1,375 处真实的引用式链接重解析，属正确性必需，不能省。

两轮合计安装阶段 433ms → 201ms（releases.md）。回归测试覆盖两个方向：定义新增后引用链接可解析、定义移除后快捷引用还原为字面文本（可见文本无 `[` 时靠 `Reference` 标记命中候选判断）。

滚动与首帧已在 10～20ms 量级，非卡顿主因；渲染不随总块数线性增长的目标已达成。

限制：解析建树（约 450～550ms）分散到每批 32 根块、批间让出 UI 线程，首屏先显示加载提示，但整篇解析完成仍需数百毫秒；首次精确派生（60～95ms）、查找、保存等依赖全文的操作仍可能短时阻塞。初始光标/状态栏位置在首次精确操作前是暂估值。结构/列宽改变时仍需线性重建行高索引。墙钟耗时已由上述基线记录；仍未实测连续输入的实际单字延迟与长时间输入的撤销边界。下一步应在真实窗口做交互测量；解析建树（450～550ms）虽已分批但仍是大头，可评估把行内解析与引用定义提取提前到后台线程，让主线程只建块树。
